世界越玩越大，备份却可以很小

服务器开得越久，存档里"路过一次就再没回去"的空地就越多，它们和主城占一样的体积。 OrzMCBackup 在备份时按玩家在每个区块里的停留时间筛选，只把真正用得到的区块写进备份。 18.6 GB 的真实世界实测备份到 2.2 GB，六档阈值逐字节比对，没有出现预期外的数据丢失。 以后想翻回更早的地图，还能把瘦身备份和旧的全量备份按区块合起来恢复。

选个版本装起来 先看实测数据
18.6 GB → 2.2 GB 同一份世界 92.7% 区块不进备份 0 例预期外丢失 默认阈值 5 分钟 支持 26.1+ 新存档格式

你大概会遇到这三种情况

它们看起来是三件事，其实是同一个原因：备份里塞进了太多没人会再回去的区块。

💾硬盘总是不够用

开服半年，存档从几百 MB 涨到十几 GB，备份目录再翻一倍。加硬盘能撑一阵，但下个半年还得加。

⏳备份挤不进日常

全量备份越跑越久，只好从每天一次改成每周一次。真出事的时候，能回滚的时间点反而变少了。

↩️想回滚却没得回

为了省空间只留下瘦身后的备份。需要翻回三个月前的地图时，直接把旧备份覆盖上去会留下空洞和回退的地形。

OrzMCBackup 只在这件事上做取舍：不活跃的区块不进备份。其余数据照常备份—— 出生点和加载器所在的区块、玩家目录、level.dat、插件数据目录都完整复制； 读不懂或损坏的文件不会被丢掉，而是原样保留并在报告里记一条。

实测：同一份世界，只改一个阈值

真实 PaperMC 26.2 世界（28,451 个文件、18,637.6 MB、3,162,906 个区块），跑了六次完整备份， 每次只改 -t（活跃时间阈值），其余参数一致：--copy-misc --parallelism 4，机械硬盘。

  • 60 秒就拿到了大部分收益。保留区块从 90.8 万降到 27.6 万，体积从 6.9 GB 掉到 2.6 GB；再往上加到 300 秒，只多省 413 MB。
  • 六档阈值都没有出现预期外的丢失。每一档都和优化前的世界逐字节比对过，阈值只决定砍多少，不会决定砍错。
  • 耗时几乎不受阈值影响。15 到 27 分钟都由读盘主导，所以选阈值的唯一代价是"多留一点旧地块"，不是"备份变慢"。
  • 怎么选：日常备份用 -t 60 到 -t 120 就够；默认的 300 更保守； -t 0 只适合归档旧周目，它会把没被玩家真正访问过的区块全部切掉。

完整数据与验证方法：阈值基准测试报告 （0 新文件 / 0 槽位伪造 / 0 锁步违规 / removedChunks 与槽位差严格吻合）

它到底做了什么

备份前逐区块做判断，只做筛选，不重写地形。

🎯按停留时间筛区块

每个区块都记录着玩家在里面累计待了多久（InhabitedTime）。够阈值就保留，不够就整块跳过。 -t 0 的意思是：没被访问过的就别进备份了。

🛡️该留的一定会留

出生点、区块加载器、传送门所在的区块会被自动识别并保留，新旧两种存档格式都认。 不会出现"主城被裁掉了"这种事。

🔒地形、实体、POI 同步处理

region、entities、poi 三个目录按同一份判断重写，避免出现地形还在、箱子或刷怪笼却没了的数据错位。

🧯读不懂的东西原样保留

损坏的区块、无法解析的 region 文件不会被丢弃，整份复制进备份，只在报告里记一条错误。 备份任务不该因为一处坏数据而少东西。

🧩认得出新存档结构

26.1 之后维度挂在 dimensions/ 下的新布局会自动递归发现， 1.2.1 以来的老布局照旧，不需要手动指路径。

🗂️输出方式随便挑

写进新目录、原地替换、打成 zip，或者只跑一遍看会砍掉多少（--dry-run）。 杂项文件默认一起复制。

🤖能挂进脚本

JSON / CSV 报告、退出码、并行度、进度输出都可配。放进 cron、面板或托管商的备份任务里不需要人盯着。

🔁瘦身备份还能合回去

merge 把瘦身备份贴回更早的全量备份，按区块槽位补全，得到一份"最新 + 全量"的地图。 这是瘦身备份敢长期替代全量备份的前提。

🧱命令行只是外壳

两套实现都同时是库：JVM 侧发布在 Maven Central，Rust 侧发布在 crates.io。 想自己定义保留规则、接进面板或备份系统，可以按下面的示例直接调，不用拼命令行。

两个实现，同一套行为：Rust 版和 Kotlin 版各自独立实现，跑同一组 24 个一致性向量； 官方 PHP 版 thanos 也作为对照一起校验，允许的差异全部登记在案。 也就是说，下面你随便挑一个装，拿到的是同一个工具。

一次备份的流程

六步，每一步都能在报告里核对。

1
找到维度

递归扫描世界目录，新老结构都覆盖

2
数清区块

统计所有 region 文件里的区块总数

3
读强制加载清单

自动找到 tickets / chunks 数据里的坐标

4
逐块判断

强制加载清单和停留时间，任一命中即保留

5
同步重写

region + entities + poi 按同一决策落盘

6
收尾

复制杂项、可选打 zip、可选原地替换、写报告

merge 怎么合：对两边都有的 region 文件，逐个区块槽位取"瘦身备份里有就用它，没有就用全量备份里的"； entities 和 poi 跟着 region 一起决定；只在全量备份里出现的文件原样复制。 真实案例：18.6 GB 全量 + 2.18 GB 瘦身备份，合并出一份约 18 GB 的完整世界。

安装与使用

两个版本命令和参数一致，按你的环境挑一个。选完之后这一屏只显示这一种装法。

适合把备份写进脚本或定时任务：装完就是一个 rust-thanos 命令，没有运行时依赖，冷启动几乎不占时间。

安装

bash — Homebrew（macOS / Linux）
brew tap orzmc/core
brew trust orzmc/core      # 新版 Homebrew 要求第三方 tap 先显式信任
brew install rust-thanos
bash — 有 Rust 工具链，或者直接下预编译包
cargo install rust-thanos      # 装到 ~/.cargo/bin

不想装工具链的话，也可以从 Release 下载对应平台的压缩包（macOS / Linux / Windows，x86_64 与 arm64 都有），解压后放进 PATH。

三条命令上手

bash — 1. 先看会砍掉多少，不写盘
rust-thanos backup /path/to/world --dry-run --report
bash — 2. 正式备份（默认阈值 5 分钟，输出打成 zip）
rust-thanos backup /path/to/world /path/to/out -t 300 --zip-output
bash — 3. 需要翻回更早的地图时合并
rust-thanos merge 更早的全量备份 瘦身备份 输出目录 --report

当前版本 0.0.5。Rust 版每条命令都要写子命令（backup / merge）， 并行度默认按 CPU 自动决定；从源码构建见 README。

当库用（二次开发）

toml — Cargo.toml
[dependencies]
rust-thanos = "0.0"
rust — 嵌入到自己的工具里，顺带保护一块主城
use rust_thanos::patterns::range::RangePattern;
use rust_thanos::world::{optimize, OptimizerRequestBuilder};

let request = OptimizerRequestBuilder::new("/path/to/world".into())
    .output(Some("/path/to/out".into()))
    .inhabited_threshold_seconds(300)
    .pattern(Box::new(RangePattern::new(-8, -8, 8, 8))) // 主城 17×17 区块永不裁剪
    .parallelism(4)
    .build();

let report = optimize(&request)?;
println!("扫描 {}，剔除 {}", report.processed_chunks, report.removed_chunks);

ChunkPattern 可以自己实现（任一命中即保留）；on_error / report_sink / metrics_sink 三个钩子负责错误、报告与指标；MemoryFS 让同一套管线跑在内存里，适合写测试。 合并侧对应 MergeRequestBuilder + merge()。

适合已经有 JVM 的机器：一个 JAR 走天下。如果你打算把备份逻辑做进自己的 JVM 程序， 同一套引擎也发布在 Maven Central，可以直接当库调用。

安装（命令行）

bash — 下载单文件 JAR（需要 JDK 17 或更新）
curl -LO https://github.com/OrzMC/OrzMCBackup/releases/download/java-v0.3.2/backup.jar
java -jar backup.jar --version

Release 页面附 backup.jar.sha256，下载后可以校验一下。

三条命令上手

bash — 1. 先看会砍掉多少，不写盘
java -jar backup.jar /path/to/world --dry-run --report
bash — 2. 正式备份（默认阈值 5 分钟，输出打成 zip）
java -jar backup.jar /path/to/world /path/to/out -t 300 --zip-output
bash — 3. 合并恢复（先出清单，确认后再落盘）
java -jar backup.jar merge 更早的全量备份 瘦身备份 输出目录 --dry-run --diff-file audit.csv
java -jar backup.jar merge 更早的全量备份 瘦身备份 输出目录 --report

当前版本 0.3.2。省略子命令即为备份；并行度用 --parallelism N 指定（默认 1）。 merge --dry-run 和 --diff-file（可审计的回退清单）目前只有 Java 版有。

当库用（二次开发）

kotlin — build.gradle.kts
dependencies {
    implementation("io.github.wangzhizhou:backup-core:0.3.2")
}
kotlin — 嵌入到自己的 JVM 程序，顺带保护一块主城
import com.jokerhub.orzmc.patterns.RangePattern
import com.jokerhub.orzmc.world.*
import java.nio.file.Paths

val report = Optimizer.run(
    OptimizerRequest(
        input = Paths.get("/path/to/world"),
        output = Paths.get("/path/to/out"),
        filter = FilterOptions(
            inhabitedThresholdSeconds = 300,
            extraPatterns = listOf(RangePattern(-8, -8, 8, 8)), // 主城 17×17 区块永不裁剪
        ),
    ),
)
println("扫描 ${report.processedChunks}，剔除 ${report.removedChunks}")

ChunkPattern 可以自己实现（任一命中即保留）；Hooks 里能挂错误回调与报告落盘； 替换 FileSystem / McaIOFactory 就能把管线跑在内存里（测试、预览都用得上）。 合并侧对应 WorldMerger.run(MergeRequest)，和 CLI 是同一套算法。

两个版本唯一的实际差别在参数细节上：Rust 版启动更快、部署更轻，并行度自动；Java 版多了合并前的 --dry-run + 差异清单。备份和合并的结果是同一套逻辑，可以混着用； 两个也都发布成了库（Maven Central / crates.io），需要二次开发时不必围着命令行转。

常见问题

动手之前最常被问到的几个问题。

会不会把不该删的区块删掉？

判断依据是存档里本来就有的数据：每个区块的玩家停留时间，加上出生点和区块加载器所在的强制加载区块。 两者任一命中就保留。默认阈值 300 秒，也就是说玩家在这个区块里待够过 5 分钟，它一定会进备份。

另外，损坏或无法解析的文件不会被跳过，而是原样复制进备份并在报告里记录。六档阈值的实测都和原世界 逐字节比对过，没有出现预期外的丢失。

需要停服吗？

建议在服务器停服，或者对一份不在写入的存档副本上跑。备份过程只读输入目录，但它假设 region 文件在读取期间 不会被服务端改写。定时任务里最简单的做法是：停服 → 备份 → 启服，或者先快照再备份。

阈值 -t 设多少合适？

日常用 60 到 120 秒：实测 60 秒就拿到了 91.3% 的剔除率，再往上一档只多省一点体积。 默认的 300 秒更保守，适合不确定玩家行为的情况。-t 0 很激进，只适合归档旧周目。

第一次用先跑 --dry-run --report，它会告诉你这份世界会保留多少区块、砍掉多少，不写任何文件。

瘦身之后想回到三个月前的地图怎么办？

只要有那份更早的全量备份，就能合回来：merge 全量备份 瘦身备份 输出目录。 逐区块取"瘦身备份里有就用它，没有就用全量备份里的"，最终得到一份既包含最新进度、又包含旧地块的完整世界。 三个目录必须互不重叠，工具会直接拒绝危险路径。

拿不准的话，Java 版可以加 --dry-run --diff-file，先看到"哪些区块会回退到旧版本、回退多久"，确认后再真正落盘。

能改保留规则，或者接进我自己的系统吗？

可以，两套实现都是库 + 命令行的双形态。JVM 侧发布在 Maven Central（backup-core）， Rust 侧发布在 crates.io（rust-thanos），都公开了配置模型和引擎入口： 自定义 ChunkPattern 决定保留哪些区块，挂 hooks 收错误和报告，还能把文件系统换成内存实现跑单测。

具体接口见上面的 安装与使用 里对应实现的「当库用」一节。

和 Aternos 的 Thanos 是什么关系？

同一套思路：按活跃时间裁剪区块。OrzMCBackup 在这之上重写了一遍，补了强制加载合并恢复（merge）、 损坏数据保留、26.1+ 新格式、报告 / 干跑 / 并行这些运营上用得着的部分，并且有两套独立实现互相校验。 允许的差异都记录在 差异对照文档里，对照中发现的问题也已经回馈给上游。

支持哪些 Minecraft 版本？

存档格式方面，1.2.1 以来的标准布局和 26.1 之后 dimensions/ 嵌套布局都支持； 区块压缩支持 RAW、ZLIB、GZIP、LZ4，外部压缩区块由 --remove-unknown 决定留不留。 服务端是 PaperMC 还是官方版没有区别，工具只读存档文件。
